Public-schema changes are driven by `src/lib/db/schema/` and the SQL files in this folder.

Run `npm run migrate` from `web/` to prepare and migrate the public schema and then migrate tenants. `npm run migrate:platform` also supports an empty database directly. Docker and CI use the same `scripts/db-prepare.mjs` → `scripts/migrate-platform.mjs` sequence before tenant migrations and seeding.

Fresh databases use the committed **0037 snapshot** as a fixed, complete checkpoint. The bootstrap generates DDL from an empty Drizzle snapshot to `meta/0037_snapshot.json` using the public Drizzle Kit API. It creates all 16 public tables and their indexes, verifies the catalog, and records the exact SQL hashes for journal entries **0000–0037** in one transaction. The cutoff stays fixed when later migrations are added. Historical SQL alone cannot build an empty database: it does not create `public.tenants`.

The platform migrator then applies subsequent SQL through the Drizzle ORM PostgreSQL migrator, including **all of 0038** and its SQL-owned immutability function and trigger. Each migration's SQL and journal insertion share the ORM transaction. A failed bootstrap leaves no partial application DDL or baseline rows. A successful baseline can remain if the subsequent migration fails; that is a baseline-only result, never completion. After an ambiguous connection/commit failure, inspect the journal and catalog before retrying.

Both CLIs select a dedicated direct connection before any SQL. Only the documented Neon AWS `ep-…-pooler.[c-N.]<region>.aws.neon.tech` format is converted to its same-endpoint direct hostname by removing the first label's terminal `-pooler`; credentials, database, port, TLS and query options are preserved. Other recognizable pooler/PgBouncer hosts are refused. Ordinary hostnames can conceal a proxy: callers must ensure the endpoint provides a direct session.

Imported clients require one host, `max=1`, `idle_timeout=0`, and `max_lifetime=0`. Both entrypoints serialize bootstrap/migration work with a bounded PostgreSQL advisory lock. Freshness requires an empty application catalog; extension-owned objects and an empty migration journal are allowed; existing default privileges and publications are refused. The presence or absence of `tenants` never establishes migration history. Existing journaled databases are not automatically rebaselined. The migrator checks the committed journal prefix before any legacy archive/clear operation and rejects unknown, modified, skipped, or duplicate journal entries. The fixed checkpoint verifies every table/column/type/null/default, primary/unique key, foreign key, check, and declared index, including ordered keys, eligibility, predicates, ordering, opclasses, and collations. Known PostgreSQL 17 deparsed check forms preserve literal case and Boolean precedence and fail closed if unrecognized. Completion also verifies the canonical standalone `tenants_slug_unique` index, both 0038 primary keys, all binding and tenant/date unique constraints, defaults, foreign key/checks/columns, and the exact immutability function/trigger.

Unqualified creation DDL runs with `search_path=public` and checks that the effective path starts with implicit `pg_catalog`, then `public`. The baseline uses transaction-local settings. `migratePlatform(sql)` restores the caller's search path and lock timeout, confirms advisory unlock, restores its temporary connection monitor, and returns only `catalog-verified` with client close pending. The CLI closes successfully before emitting `complete`. Unexpected connection loss ends the native client and aborts the operation without retry or replacement-connection cleanup. `UNKNOWN` means a commit acknowledgement was unresolved; inspect before retrying. `COMMITTED_UNVERIFIED` means the ORM confirmed commit but catalog verification failed; it is never labeled a SQL rollback. Cleanup failures preserve the original operational cause and known commit state and exit nonzero.

For an existing **unjournaled or partial database**, stop and reconcile manually: take a backup, compare the actual catalog and data with the committed migrations, identify which SQL (including SQL-owned functions and triggers) truly ran, and review a recovery plan before changing either data or journal rows. Do not stamp every journal entry from table existence or use `drizzle-kit push` as migration proof. The legacy `setup-production.ts` push utility is outside this bootstrap path.

The SQL files here remain the canonical migration trail, snapshots, and review source. `0010_public_schema_catchup.sql` reconciles the older journal/snapshot history; `legacy/` contains earlier handwritten patches outside the metadata journal.
